# Real-Time Chat Assessment

A small real-time chat application with a React/Vite frontend and an Express/Socket.io backend. Messages are held in backend process memory and shared with connected clients in real time.

## Features

- Enter a username and send a message with the Send button or Enter.
- Load message history when the frontend opens or refreshes.
- Receive new messages through Socket.io without refreshing.
- Display each message's username, text, and timestamp.
- Show the chat connection state and request errors.

## Tech stack

- Frontend: React, Vite, `socket.io-client`, plain CSS
- Backend: Node.js, Express, Socket.io, CORS, dotenv
- No database or authentication

## Prerequisites

- Node.js compatible with the installed Vite version (Node.js 20.19+ or 22.12+ recommended)
- npm

## Setup and run

Install and start the backend in one terminal:

```bash
cd backend
npm install
npm run dev
```

The backend listens on `http://localhost:3000` by default. `npm start` runs it without the development file watcher.

In a second terminal, install and start the frontend:

```bash
cd frontend
npm install
npm run dev
```

Open the Vite URL shown in the terminal (by default `http://localhost:5173`). Start the backend before using the chat.

## Environment variables

Backend settings are read from `backend/.env` using dotenv. Copy `.env.example` to `.env` to customize them:

| Variable | Default | Purpose |
| --- | --- | --- |
| `PORT` | `3000` | Backend HTTP and Socket.io port |
| `FRONTEND_ORIGIN` | `http://localhost:5173` | Origin allowed by REST and Socket.io CORS |

The frontend uses `VITE_BACKEND_URL` for the backend base URL and defaults to `http://localhost:3000`. To override it, create `frontend/.env` with, for example:

```dotenv
VITE_BACKEND_URL=http://localhost:3000
```

Restart the Vite development server after changing frontend environment variables. `.env` files are ignored; `.env.example` files are shareable and contain no secrets.

## HTTP API

All endpoints are served by the backend at `http://localhost:3000` by default.

### `GET /api/messages`

Returns the current in-memory message history as an array.

### `POST /api/messages`

Accepts JSON with non-empty `username` and `text` fields:

```json
{
  "username": "Sam",
  "text": "Hello"
}
```

Returns the created message with HTTP `201`:

```json
{
  "id": "generated-uuid",
  "username": "Sam",
  "text": "Hello",
  "timestamp": "2026-09-28T14:17:03.049Z"
}
```

Invalid or empty fields return HTTP `400` with an `error` message. A valid POST stores the message in memory and broadcasts it through Socket.io.

## Socket.io events

- `connection` / `disconnect`: the backend handles client connection lifecycle and logs it.
- `new_message`: the backend broadcasts a newly created message; the frontend listens and updates its message list.
- `send_message`: the backend accepts this event from Socket.io clients, validates and stores the message, then broadcasts `new_message`. It responds through an optional acknowledgement callback or `message_error` on invalid input.
- `message_error`: emitted by the backend for socket message errors when no acknowledgement callback is supplied; the frontend also listens for it.

The frontend currently sends through `POST /api/messages`; the backend POST handler performs the same storage and broadcast. The frontend receives the resulting `new_message` event, and also merges the POST response into its own state. Message IDs prevent duplicate display when both paths update the sender.

## Design decisions and assumptions

- Messages are stored in a JavaScript array in the backend process. They are available to refreshes while that process is running and are lost when it stops or restarts.
- REST is used to send messages and load history; Socket.io delivers live updates.
- Message timestamps are generated by the backend in ISO 8601 format and formatted for display by the browser's locale.
- The default CORS origin is the local Vite development URL. Set `FRONTEND_ORIGIN` if the frontend is served from a different origin.
- The frontend and backend are intentionally small and use one main chat component and one backend entry point.

## Testing

There is no automated backend test suite in this project. Check the frontend scripts from `frontend/`:

```bash
npm run lint
npm run build
```

Manual end-to-end check:

1. Start the backend and frontend using the commands above.
2. Open the frontend in two browser tabs at the same allowed origin.
3. Send a message using both Enter and the Send button; confirm it appears in the sender and other tab without refreshing.
4. Refresh a tab and confirm the message is loaded from `GET /api/messages`.
5. Try an empty username or message and confirm the frontend displays validation feedback.
6. Stop the backend and confirm the frontend reports a connection or request problem.

## Known limitations

- Message history is not durable and is lost when the backend process restarts.
- There is no user identity, authentication, or per-user message ownership; the username is supplied by each client.
- CORS allows one configured frontend origin.
- The backend has no automated test script.
